# 做一个断电也不变砖的 OTA：四个我踩过的坑

> 这是写完 [stm32-ota-bootloader](https://github.com/wenjialei15/stm32-ota-bootloader) 之后整理的复盘。
> 代码在 STM32F103C8T6 上跑，64 KB Flash 划出双槽做 A/B 升级。
> 下面四件事，每一件我都先想错了一次。

## 背景：难点不在"传固件"

OTA 听起来像"加个下载功能"：从串口收固件、写进 Flash、跳过去跑。三句话就能说完。

真正难的是**擦写 Flash 的任意时刻断电**。Flash 的物理特性决定了三件事：

1. 擦除最小单位是 1 KB 页，不能只擦一个字节
2. 编程最小单位是 16 位半字
3. **只能把 1 写成 0，想变回 1 必须整页擦除**

第三条最要命。它意味着"修改一个字段"实际上是"擦掉整页、重写整页"。而这中间的任何一毫秒断电，那一页就废了。

如果保存"当前该启动哪个槽"的元数据所在的那一页废了，设备就不知道该跑什么——也就是变砖。

## 坑一：以为双备份就是"写两份"

我最初的方案很直白：元数据存两份，A 份写坏了就读 B 份。

然后我发现一个问题：**写 B 份的时候，B 份本身也可能被写坏**。如果 A 和 B 同时处于半写状态，就全完了。

于是我加了一个"提交标志"：先写标志位表示"正在更新"，写完再清掉。读的时候看到标志就说明这份不可信。

写完才意识到这是套娃——标志位本身也要掉电保护，标志位写一半怎么办？

真正干净的方案是**永远不覆盖有效数据**：

```
读 A、B 两份，比较序号，确定哪份是旧的
擦除旧的那份所在的页
写入新记录
回读校验 CRC
```

关键在第一步：**擦之前先确认另一份是完好的**。这样任意时刻断电，磁盘上至少有一份完整记录：

| 断电时机 | 结果 |
| --- | --- |
| 擦除中 | 旧份损坏，另一份仍完整 → 用另一份，最多丢失最后一次提交 |
| 写入中 | 同上，新记录 CRC 不过被忽略 |
| 写完未校验 | 两份都完整，序号大的胜出 → 正确 |

这个方案里**不存在"正在更新"这个状态**，所以也不需要标志位，也就没有标志位本身的掉电问题。

删掉一个状态，比给它加保护更彻底。

## 坑二：序号比较在 0xFFFFFFFF 之后失效

"取序号大的那份"——听起来天经地义：

```c
*out = (a.seq > b.seq) ? a : b;
```

然后我想到一个问题：序号是 32 位，写满 42 亿次之后会回到 0。回到 0 的那一份，序号比旧的那份小，会被判成旧的，**最新的数据反而被忽略**。

42 亿次听起来很远，但元数据每次启动都可能写（试运行计数），一天重启 100 次的设备两年就到头了。

正确做法是 TCP 比较序号那套——用有符号差值：

```c
static int seq_is_newer(uint32_t a, uint32_t b)
{
    return (int32_t)(a - b) > 0;
}
```

减法的模运算会自动处理回绕：`1 - 0xFFFFFFFE = 3`，转成有符号数是正数，所以 1 比 0xFFFFFFFE 新。

这个细节我在测试里专门造了两个样本验证：`0xFFFFFFFE` 和 `1`，朴素的 `>` 会选错，差值法选对。

## 坑三：跳转成功了，但应用跑几秒就死

第一次把 Bootloader 和应用串起来时，现象极其迷惑：应用能启动、能打印心跳，然后**过几秒突然死机**。改代码没用，复位又能跑几秒。

原因在 Cortex-M3 的 `VTOR` 寄存器。

复位后 `VTOR` 指向 `0x08000000`，也就是 Bootloader 的向量表。跳到应用（`0x08003000`）之后，如果不重设 `VTOR`，应用里**任何一个中断**都会跳回 Bootloader 的向量表——而那里已经不是这次运行的上下文了。

为什么是"几秒后"？因为我的应用用 `delay_cycles` 忙等，没有开任何中断。几秒后某个外设中断（或者我自己后来加的串口接收）一触发，就跳飞了。

跳转前必须做完四件事，顺序不能乱：

```c
irq_disable();          /* 1. 关全局中断 */
SYST_CSR = 0;           /* 2. 关 SysTick，它是唯一会自己触发的异常源 */
SCB_VTOR = app_base;    /* 3. 重定位向量表 */
dsb(); isb();           /*    确保上面三件事真的生效 */
set_msp(app_sp);        /* 4. 换成应用自己的栈顶 */
((void (*)(void))app_entry)();
```

第 4 步容易被忽略：应用的向量表第 0 项是它自己的初始栈顶，不能沿用 Bootloader 的栈。混用两个栈，爆栈的位置会非常诡异。

还有一个隐蔽的坑：`cpsid i` 这类内联汇编必须带 `"memory"` clobber。否则编译器不知道中断被关了，会把中断里访问的变量缓存到寄存器里，优化出莫名其妙的 bug。

```c
static inline void irq_disable(void)
{
    __asm__ volatile("cpsid i" ::: "memory");
}
```

## 坑四：回滚了，但元数据是脏的

第四个坑是我写端到端测试时抓到的。

回滚逻辑本身很快写完了：新固件连续 3 次没"报到"，就退回旧槽。测试也过了——**每次上电确实都跳到旧槽**。

但我在测试里多写了一句断言，查回滚后的元数据：

```c
CHECK_EQ(meta.pending_slot, META_NONE);
```

挂了。

因为回滚分支只返回了"跳哪个槽"，没有清理 `pending`。于是元数据永远停在"有一个待确认的升级"，而每次上电都命中"retry ≥ 上限"分支跳回旧槽。

功能上完全正确，设备能用。但状态是矛盾的：`pending` 说有个升级等着确认，`active` 说当前跑的是旧固件。后续 `STATUS` 查询、下一次升级的 `BEGIN` 都会看到这个脏状态。

修法是在决策结果里加一个显式标志：

```c
typedef struct {
    boot_action_t action;
    uint32_t slot;
    int bump_retry;      /* 试运行计数 +1 */
    int clear_pending;   /* 回滚时清掉 pending */
    boot_reason_t reason;
} boot_plan_t;
```

让"纯粹算跳哪"的函数顺手把"需要修什么"也说出来，调用方一起落盘。

**这类 bug 手工点几下永远发现不了**，因为表象是好的。只有把"回滚后元数据必须干净"写成断言，才会暴露。

## 顺带说一个设计决定：为什么必须编两份固件

A/B 槽意味着同一个应用要能从两个不同地址启动。

第一反应是"一份固件跑两个槽"。不行——Cortex-M 的向量表项、字面量池里的函数地址、跳转指令全是绝对地址。链接到 `0x08003000` 的固件放到 `0x08009000` 会全线跑飞。

要么做位置无关代码（PIC，工作量大且影响性能），要么**每个槽单独链接一份**。我选了后者：

```makefile
$(BUILD)/app_a.elf: ... -Wl,--defsym=SLOT_BASE=0x08003000 ...
$(BUILD)/app_b.elf: ... -Wl,--defsym=SLOT_BASE=0x08009000 ...
```

代价是发布时有两个固件。但换来的是清晰——每个槽的固件都知道自己在哪，不需要任何运行时重定位。

## 最后：为什么这些坑都是测试抓到的

四个坑里，三个是自动化测试发现的，包括那个最容易漏的"元数据脏"。

关键在于**把硬件摘出去**。镜像校验、元数据提交、启动决策这三个模块不碰任何寄存器，Flash 访问通过回调注入：

```c
typedef struct {
    int (*read)(uint32_t addr, void *buf, uint32_t len);
    int (*erase)(uint32_t addr, uint32_t len);
    int (*write)(uint32_t addr, const void *buf, uint32_t len);
} storage_if_t;
```

于是掉电这种最难的场景，可以在 PC 上用一块 `malloc` 出来的内存模拟：

```c
if (s_current->power_cut_at >= 0 && s_current->op_count >= s_current->power_cut_at) {
    memset(s_current->mem + off, 0xFF, len / 2);  /* 擦到一半掉电 */
    s_current->power_lost = 1;
    return -1;
}
```

然后遍历每一个断电点，检查还能不能恢复到一致状态。我测了 6 个时机，全部能恢复。

整份测试 210 项断言，在 CI 上跑，不需要板子。**硬件相关的部分做得越薄，能测的部分就越多**——这是这个项目里我认为最值钱的一条经验。
